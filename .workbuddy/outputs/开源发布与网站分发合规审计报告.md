# BrewPing 开源发布与网站直接分发合规审计报告

审计日期：2026-09-16
审计对象：github.com/banmu123/BrewPing（HEAD = `4cfb53c`）
审计方式：实读仓库代码 / Package.swift / npm 清单 / 打包脚本 / Info.plist / 隐私清单 / 素材目录，未采信 README 自述
法律定性说明：本报告是**工程与合规事实排查**，不构成法律意见；涉及商标、许可解释的事项已标注「需人工确认」。

## A. 总体结论

### ⚠️ 有需要修改的问题 —— **修改后可以发布**

核心判断：**没有发现会阻止你分发的许可证冲突或再分发违规**——项目零第三方二进制打包、零 SPM 依赖、CLIs 只是检测调用、无 telemetry、无硬编码凭据，macOS 签名公证链条完整规范。

但有一个**必须先解决**的硬伤：**仓库声称 MIT，却根本没有 LICENSE 文件**（历史上也从未有过）。这不是形式问题：没有许可证文本的仓库在法律上默认是「保留所有权利」，他人无法合法使用、修改、分发你的代码——这与「开源项目 + 官网免费下载」的定位直接冲突。

| 结论项 | 状态 |
|---|---|
| 开源许可证 | ❌ **无 LICENSE 文件**（README 声称 MIT） |
| 第三方依赖许可证冲突 | ✅ 未发现（且 DMG 不含任何第三方依赖） |
| 再分发第三方软件 | ✅ 未发现（不含 Node / OpenCode / Claude / Codex / pi） |
| macOS 签名公证链 | ✅ 规范（Hardened Runtime + 公证 + staple + spctl + sha256） |
| 商标/品牌误导 | ⚠️ 声明存在于 README 与 iOS 端，桌面端与官网待确认 |
| 隐私实现 vs 隐私政策 | ⚠️ 主链路一致，但 relay-server 与 Windows 日志记录存在偏差 |
| 硬编码凭据 | ✅ 未发现真实凭据 |

**最终结论句：当前版本是否适合公开发布并在 commitbrew.com 提供 BrewPing Desktop 下载 —— 「修改后可以」（补 LICENSE 等 P0/P1 项后即可）。**

## B. P0 / P1 / P2 问题清单

### 🔴 P0 —— 发布前必须修

#### P0-1 仓库没有任何 LICENSE 文件，但 README 声明 MIT

- **文件**：`README.md:52-53`（License 徽章 `License-MIT-green`）、`README.md:283-285`（`## License` → `MIT`）、`README.zh-CN.md:279` 附近
- **问题**：全仓（含 git 全部历史）搜索 `LICENSE / COPYING / NOTICE` → **零命中**。`git log --all --diff-filter=A` 中也没有任何许可证文件被添加过的记录。
- **风险**：MIT 的授权只有在随附许可证全文时才生效。当前状态下：①他人 fork/使用/再分发缺乏法律依据；②GitHub 与各类合规扫描会把它识别为「无许可证」；③官网提供二进制下载却没有许可证文本，是分发方最容易被质疑的点。
- **修改建议**：
  1. 根目录新增 `LICENSE`（MIT 全文 + `Copyright (c) 2026 <版权主体>`）；
  2. 确认版权主体是**个人姓名**还是**公司/组织实体**（需人工确认，影响后续商业化与维权）；
  3. 如需收录第三方许可声明，可另加 `THIRD-PARTY-NOTICES.md`；
  4. README 的 License 段补一句链接：`MIT — see [LICENSE](./LICENSE)`。

#### P0-2 README 的 MIT 声明与实际状态不一致（声明的延续问题）

- **文件**：同上
- **问题**：这是 P0-1 的另一面——当前「声明」与「事实」不一致。
- **风险**：对外展示为开源，实际未提供授权，属于**陈述与事实不符**的低级但高风险问题（在商标/许可纠纷中尤其被动）。
- **修改建议**：与 P0-1 一并修复，修复后二者自动一致。

### 🟠 P1 —— 强烈建议发布前修

#### P1-1 macOS 两个打包脚本产出不同的 Bundle Identifier

- **文件**：`build-app.sh:85`（`local.brewping.desktop`）vs `Scripts/build-mac-app.sh:46`（`com.brewping.desktop`）；iOS 侧为 `com.brewping.ios`
- **问题**：两套脚本生成不同 bundle id，其中 `local.` 前缀不是反向域名形式、也不受你控制。
- **风险**：①用户升级路径上可能出现偏好设置 / 钥匙串 / TCC 权限（本地网络）被当成两个不同 App；②`local.` 与企业环境 MDM、以及未来可能的 App Store 化不兼容；③对外显得不专业且与 `com.brewping.*` 系列不一致。
- **修改建议**：统一为 `com.brewping.desktop`（与 iOS 的 `com.brewping.ios` 保持同族），二选一保留一套打包脚本或让两者读取同一常量。

#### P1-2 仓库 git 跟踪了 iOS Debug 构建产物（含编译后的二进制）

- **文件**：`ios/build-device/Debug-iphoneos/BrewPing.app/**`（git 已跟踪：可执行文件 `BrewPing`、`BrewPing.debug.dylib`、Info.plist、`Watch/BrewPing Watch App.app/**`）
- **问题**：`.gitignore` 后来加了 `ios/build*/`（见 `.gitignore` 注释，明确写了这些是**过期**产物、配置可能误导），但**已经跟踪的文件不受 ignore 影响**，仍然在仓库里并会随开源发布出去。
- **风险**：①把 Debug 二进制当源码发布，体积与噪音；②其中 Info.plist 可能缺少当前版本的权限键（`.gitignore` 注释自己就警示了这点），被第三方误当作「当前实现」从而做出错误判断；③可能夹带本机路径、签名/描述文件信息。
- **修改建议**：`git rm -r --cached ios/build-device && git commit`（如需彻底清除历史记录，需 `git filter-repo`，属破坏性操作，需人工确认是否值得）。

#### P1-3 relay-server 无鉴权且把完整消息 payload 写进日志

- **文件**：`relay-server/src/utils/auth.ts:22-27`（`if (mode === 'anonymous') { next(); return }` REST 全放行；WS 只解析 `role/deviceId` 不校验身份）、`relay-server/src/server.ts:163`（`logger.info('MESSAGE', ..., { payload: msg.payload })`）
- **问题**：该服务在 `README.md:240` 被描述为「未启用 / 客户端无连接代码」，但源码就在公开仓库里，且具备中转命令内容并落日志的能力。
- **风险**：①若用户自行部署，等于开放一个无需鉴权的命令中转站；②它的日志记录行为与 `docs/privacy.html` 的「不记录命令内容 / 不经我们服务器」承诺相冲突——一旦被理解为产品的一部分，隐私陈述就会失真。
- **修改建议**（三选一，按你的计划定）：明确标注 `experimental / not enabled / not for deployment` 并加 README 警告；或补鉴权 + 禁止记录 payload；或暂不随开源仓库发布。

#### P1-4 商标免责声明在桌面端与官网缺失

- **文件**：已有——`README.md:279`、`README.zh-CN.md:279`、`ios/BrewPing/BrewPingConfig.swift:28-30`（App 内声明 + 中英 Localizable + HelpView 展示）
- **缺口**：`Sources/BrewPingDesktop/`、`Sources/BrewPingwinDesktop/src/`、`Android/` 检索 `trademark` → **零命中**；官网下载页内容**无法从仓库确认**（仓库无官网源码）。
- **风险**：官网下载页是最直接的对外触点，若缺少「与 OpenCode / Anthropic / OpenAI / Codex 等无隶属、背书、赞助关系」的声明，品牌误导风险高于仓库内部。
- **修改建议**：下载页加一行中英双语声明，措辞与 `README.md:279` 保持一致；桌面端 About/设置页补一句。
