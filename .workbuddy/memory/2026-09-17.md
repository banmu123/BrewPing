## TestFlight 发布后「仍然检测不出设备」—— 第二轮根因：`policyDeniedCode` 写错

背景：昨天移除 `hasEverBeenGranted` 门禁 + 修 8s 竞态后发布，用户反馈**依然扫不到设备**。
（昨晚那版 build 里的 `self.` 编译修复**仍未提交**，是从工作区直接构建的。）

### 先排除的（都正常）
- 广播侧没问题：本机 `dns-sd -B _brewping._tcp` 能看到 `Chenzk`（`Chenzk.local.:8787`，
  TXT 含 `platform=macOS deviceId=bp_mac_09c23ab3`）—— 网络与桌面端广播都是好的。
- `Info.plist` 三项齐全（`NSBonjourServices=_brewping._tcp`、`NSLocalNetworkUsageDescription`、
  `NSAllowsLocalNetworking`）；pbxproj Debug(:470-479) / Release(:493-502) 逐字段一致，
  `GENERATE_INFOPLIST_FILE=NO` + `INFOPLIST_FILE=BrewPing/Info.plist`。
- iOS 侧**无** entitlements 文件、无 `com.apple.developer.networking.multicast`——Bonjour 浏览
  **不需要**该授权（只有自己发 UDP 广播才需要），不是本轮原因。

### 真根因：`kDNSServiceErr_PolicyDenied` 的取值写错了
- 代码 `BonjourDiscovery.swift` 里 `policyDeniedCode = DNSServiceErrorType(-65555)`，
  而 **-65555 是 `kDNSServiceErr_NoAuth`**；真值是 **-65570**
  （本机 SDK 头文件实证：`$(xcrun --show-sdk-path)/usr/include/dns_sd.h:801`）。
  Apple TN3179 也是 -65570。旧注释「C 匿名枚举成员 Swift 不可见」是**误判** ——
  `kDNSServiceErr_PolicyDenied` / `kDNSServiceErr_NotPermitted` 在 Swift 里**可直接引用**（已 typecheck 验证）。
- 后果链：本地网络被拒 → iOS 回 `.waiting(.dns(-65570))` → 代码不认 → 判成 `.requesting`
  → 浏览窗口续期 3 次（~32s）后安静收尾 → **既不显示「被拒 + 打开系统设置」，也永远扫不到设备**。
  与"TestFlight 上死活检测不出"完全吻合。

### 本轮改动（3 处代码 + 1 处文档）
1. `BonjourDiscovery.swift`：`policyDeniedCode` 改用 C 符号 `kDNSServiceErr_PolicyDenied`；
   新增 `notPermittedCode = kDNSServiceErr_NotPermitted`(-65571)；`isPolicyDenied` 两者都认。
   顶部类型注释的错误码同步更正。
2. `ContentView.swift`：加 `.onReceive(bonjour.$localNetwork) { _ in permissions.refresh() }` ——
   自动探测（onAppear 无条件 `startSearching()`）得出的授权结论此前**从不**回灌 `PermissionCenter`
   （它只在 `attach()` 同步一次，之后只有用户手点「授权」才轮询）→ `allGranted` 恒为假。
3. `ContentView.swift` `discoverForSheet()`：一无所获时把 `bonjour.lastBrowseError`
   追加成 `(diag: dns(-65570))` —— 让下一个 TF 包**不用挂调试器**就能读出卡在哪。
4. 诊断文档 §7 错误码对照表勘误（原表把 -65555 当 PolicyDenied，是这个 bug 的来源）。

### 用户答复（推翻了上面的假设，但修复本身仍成立）
- 手机「本地网络」开关 **是开着的**；TF 首启**弹过系统框并点了「允许」**。
  → 也就是**授权没问题**，`-65570` 那个 bug 不是本次现象的原因（但它确实存在：
  被拒的用户此前永远拿不到「被拒 + 打开设置」的提示，修掉是对的）。
- 于是只剩两条链：**结果压根没回来** vs **结果回来了但解析失败**。
  已排除展示侧：`nearbyCard` 无额外门槛，`discoveredHosts` 非空就渲染。

### 为下一个包加的自诊断（定位完要删）

  （`diag: browser=… results=… hosts=… ln=… err=…`）。

## 14:3x 用户回了诊断行：`browser=cancelled results=1 hosts=0 ln=granted err=none` → resolve 环节专项修复

**关键推论**：诊断行能显示 = `discoverySettled==true` = `resolvers` 已空。结果到达过（results=1）但没解析成
host —— 要么 `didNotResolve` 触发了（**错误码此前整个被丢掉**），要么 `didResolveAddress` 回调了但地址不可用，
要么回调根本没来。授权 / plist / 广播侧均已排除（Mac 上 `dns-sd` 能看到 `Chenzk.local.:8787 platform=macOS`）。

### 审计结论（改前）
- `resolvers` dict 强持有 service → §2A「对象被提前释放」不成立；
- `resolve(withTimeout:)` 隐式调度到「创建线程的 current run loop、default 模式」→ 依赖主线程 + 会被
  滑动（tracking 模式）饿住；
- `didNotResolve` 的 `errorDict` 整个丢弃 → 失败原因不可见；
- `startSearching()` 顶部调 `stopSearching()` → scenePhase 回前台 / 手动发现 / 权限卡重试的每次重启
  都会杀掉在途 resolve（违反 Browser/Resolve 生命周期解耦）；
- resolve 无 STUCK 看门狗 → 「没进回调」伪装成「解析慢」。

### 本轮改动（全部在 `ios/BrewPing/BonjourDiscovery.swift`）
1. `ResolveStage` 状态机（found/resolving/resolved/failed/timedOut/stuck/cancelled）+ `ResolveStats`
   计数（started/resolved/failed/stuck/cancelled），并入 `diagnosticText`。
2. resolve 显式 `schedule(in: .main, forMode: .common)`（钉死线程与模式，滑动不饿死）。
3. `TrackedNetService`（NetService 子类，deinit 打日志）——注意 `init(domain:type:name:)` 是**便利构造器**，
   子类直接继承、不能 override；`Data` 取 sockaddr 要用 `withUnsafeBytes`（没有 `.baseAddress` 属性）。
4. resolve 看门狗：超时(10s，诊断期临时，定位后回 4s)+3s 仍无回调 → STUCK + 强制收尾。
5. `didNotResolve` 全量记录 errorDict（codes/keys），错误码为 -65568 → 判 timedOut；
   `didResolveAddress` 记录 addrs/v4/v6/hostName 与选用结果。
6. `startSearching()` 改为只 `stopBrowsing()`：在途 resolve 跨重启存活；`pendingOS` 也不随重启清
   （在途 resolver 完成时要用，否则 Windows 设备错标 Mac）；完整清理只在 `stopSearching()`。
7. 全链路日志：FOUND（含 skip 原因）/ RESOLVE_STARTED / CALLBACK(didResolveAddress|didNotResolve) /
   RESOLVED / FAILED / STUCK / CANCELLED / service deinit，均带 elapsed ms。

## 15:59 决定性证据：`elapsed=58ms + code=none + domain2=local(无点)` → didNotResolve 空字典、非本地清理

- 用户新 diag（session=2）：`started=1 ok=0 fail=1 stuck=0 code=none domain=none keys=none elapsed=58ms
  name=Chenzk type=_brewping._tcp. domain2=local`。
- **离线钉死的事实**：
  ① 失败来自 `didNotResolve` 路径 —— `ResolveFailureInfo` 只有两条产出路径：didNotResolve 用
  `sender.domain`（NetService 归一化 → `local` 无点），fallback 硬编码 `"local."` 带点；diag 的
  `domain2=local` 无点 → 只有 didNotResolve 能产出。**§10「DID_RESOLVE 后提取失败」排除**。
  ② **不是我们主动 cancel**：我们所有 stop()（teardownResolvers/finishResolve）都先 `delegate=nil`
  再 stop → 系统不会回调、也写不进 lastResolveFailure；58ms 时也没有任何 teardown 会被触发。
  → 系统在 delegate 挂着时主动回调 didNotResolve，**桥接后 errorDict 为空**（keys=none）。
  ③ 空字典两种可能：情况 A 系统真给空 / 情况 C [String: NSNumber] 桥接丢值 —— 本轮日志
  （errorCount + dict description + 逐对 k=v(type)）用于区分；若仍 count=0，需 ObjC 层取证。
- **本轮改动**（仅 BonjourDiscovery.swift，遵守 §13 白名单）：
  ① 事件链补全：RESOLVE_REQUEST（含 initDomain/initType/main）→ SCHEDULE（loop=main mode=common）
  → RESOLVE_STARTED（oid）→ DID_RESOLVE / DID_NOT_RESOLVE（oid + main 线程 + port 原始值）；
  ② FOUND 增加 `srcType/srcDomain`（NWBrowser 原始值 vs 我们的构造参数，§9 normalization 取证）；
  ③ **补实现 `netServiceDidStop`**（此前盲区）：DID_STOP + wasResolving；系统中途停 service 时
  立即按失败收尾，不再挂到 13s 看门狗；
  ④ didNotResolve 全量取证：errorCount / keys / values / pairs(k=v(类型)) / dict description。
- 待下一个包：DID_NOT_RESOLVE 的 errorCount/pairs —— 若非空，code 直接收口；若空，A/C 之辨别。
