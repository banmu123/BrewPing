## 梳理「配置生效流程」（用户提问，审计型回答，无代码改动）

**结论：不需要重启服务或应用，也不需要手动触发。** 实测证据链：

- **前端触发点有三个**（`App.tsx`）：

  2. 指纹 effect —— `models.configVersion` 与上次不同就重拉（L484-492，防自激用 `useRef` 比较）

## iOS 自动同步能力审计（用户提问，审计型，无改动）

**结论：iOS 目前不能自动同步模型配置变更。** 三个硬事实：

- 🚨 **iOS 全仓 0 处解析 `configVersion`**（`Grep configVersion` 只命中 Windows 端 TS/RS，iOS 侧零命中）→ 指纹机制**根本没接到 iOS**。`ModelsResponse`（`ModelCatalog.swift` L16-35）只有 `agentId/providers/activeModelId/preferredModelId`，**没有 `configVersion` 字段**。
- 🚨 **真正的自动轮询路径被 `loadedKey` 堵死**：`ContentView.runStatusLoop()` **每 5 秒**调 `refreshStatus()` → 尾部 `await refreshModels()` → `modelStore.refresh(device:agentID:)`（**不带 force**，L1215）→ 命中 `if !force, loadedKey == key { return }`（L120）**直接返回，不发请求**。所以"5 秒轮询"对模型列表**完全不生效**，只对 status/agent 生效。
- **手动触发才是实际路径**：全仓 `force: true` 共 6 处 —— `ConversationListView` 下拉刷新(`.refreshable`)/重连(`onChange(of: online)`)/Agent 操作 ×4、`ConversationDetailView` ×2、`WatchConnectivityManager` 切 Agent 后 ×1。**只有下拉刷新是用户随手可用的**。
- **同步范围**：iOS `ModelStore` 是**单例** `shared`，`models` 是**一份全局列表**（非 per-device、非 per-conversation）。缓存键 = `deviceID/agentID`，所以切设备/切 Agent 会重拉一次。
- **Watch**：靠 WCSession `knownModels` 下发，仅在**切 Agent 成功后**立刻拉一次并推送（`refreshModelsAndPush`），另有 `knownModelsAgent` 做归属校验。
- 🚨 **新发现的真 bug（未修）**：`ModelPickerView`（iPhone 的模型选择页，L364）调 `store.select(model.id)` —— **丢掉了 `providerID`**！而 `ModelCatalog.swift` L240 注释明写"providerId 与 modelId 成对提交：同名模型可来自多个 provider，缺了它 opencode 会拼出错误的 `provider/model`"。`ConversationDetailView.selectModel` L594 是**对的**（传了 pair），只有这个备用 picker 漏了。
- ⚠️ **`canSwitch = !unsupported && models.count > 1`**（L95）→ **只有 1 个模型时整个模型 Section 不渲染**。当前 xiaomi 只有 `mimo-v2.5-pro` 一个模型 → **iOS 上永远看不到模型入口**。这是 iOS 端"没得选"的主因，与同步无关。

## 审计：改厂商配置后多对话是否同步（用户提问，无改动）

**结论：列表会全同步；"当前生效模型"**看各对话有没有自己的覆盖**，不能一概而论。**

- 🚨 **关键机制：模型不是快照，是每次执行时现算**（`command_runner.rs` L278-307）：
  ```rust
  let (model, model_provider) = match conv_model {      // 对话级覆盖
      Some(id) => (Some(id), conv.model_provider_override),
      None     => (state.model_prefs.get(&agent_id), state.model_prefs.get_provider(&agent_id)),
  };
  ```
  → **源数据一变，下次发消息自动用新值；已写进对话记录的是"id 指针"而非配置快照。**
- **优先级链**：对话级覆盖 `model_override`+`model_provider_override`（成对）> Agent 全局偏好 `~/.brewping/models.json`（**key 只有 agent_id，全对话共享一份**）> 配置里的 active。
- 🚨 **三类行为**：
  1. **没设过覆盖的对话**（多数）→ **全部跟着变**（改 provider baseURL/Key、改默认模型、删除默认模型都算）。这是"所有对话同步更新"的那一类。
  2. **设过覆盖的对话** → **绑定不变、不跟着变**。这正是 `App.tsx` L580 那句 "This chat uses its own model. Other chats are unaffected." 的承诺。
  3. ⚠️ **覆盖的模型被删除/改名后 → 静默失效**：`command_runner` 把 `provider/model` **原样拼成 `--model` 传下去，不校验是否还存在**（L302-307 + `headless_args` L38-41）→ opencode 侧报错。前端 `currentModelKey`（L778-783）匹配不到就变空串 → **模型下拉显示空白**，但 `modelOverride` 仍在库里、**不会自动清除**，需要用户手动选一次新模型或"跟随 Agent 配置"。
- **生效时机**：`POST /api/agents/models/default` 或 `PATCH /api/conversations/<id>` **写完立即落盘**；下一个命令的 `command_runner` 现读 → **下一条消息即生效**。已在跑的进程不热加载（改的是下次 spawn 的参数）。
- **不自动同步 / 需重载的场景**：① 设过对话级覆盖；② 后端改了配置但前端列表没重拉（关设置页/切 Agent/下拉刷新才重拉，见"配置指纹"节）；③ 覆盖的模型已不存在（需手动重选）；④ 已在运行的 opencode 进程不感知。
- ⚠️ **前端缺口（未修）**：模型下拉渲染条件是 `modelOptions.length > 0`（`App.tsx` L1164）。若配置里所有 provider 都没了 → 下拉整个消失，但对话可能还留着 `modelOverride` → 用户**既看不到覆盖的存在，也无法清除它**。建议后续加"覆盖失效"提示行 + 一键回落。

### 追问澄清：「切换对话 = 重新拉一次模型列表」

**只对了一半。** 判据是 `effectiveAgentId = activeConv?.agentId ?? draftAgentId`（`App.tsx` L459）—— 列表 effect（L469-472）**只依赖 `effectiveAgentId`，依赖数组里根本没有 `activeConvId`**。

- 🚨 **同 Agent 内切对话 → 不重拉**：opencode 下所有对话 `agentId` 都是 `"opencode"` → `effectiveAgentId` 字符串不变 → effect 不触发。**列表本来就是 Agent 级的，同 Agent 的对话共用同一份**，所以不重拉也不影响正确性。
- ✅ **切到不同 Agent 的对话 → 会重拉**（`effectiveAgentId` 变）。
- ✅ **iOS 侧反而每次切对话都重拉**：`ConversationDetailView` 的 `.task(id: agentId)` —— 换对话时视图按 `ConversationRoute.existing(conv.id)` 是**新实例**，`.task` 会重新跑；但 `ModelStore` 内部按 `device/agentID` 去重，**同 Agent 时依然直接 return**（不实际发请求），最终效果与桌面端一致。
- 💡 **结论**：真正让列表更新的三条路仍是 —— ① 关设置页（降沿 effect）② 切 Agent ③ 指纹变化（现含 iOS）。**切对话本身不是其中一条**（同 Agent 时）。
