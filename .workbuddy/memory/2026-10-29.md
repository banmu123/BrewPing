# 2026-10-29（第二批）— 审批结果关联机制

## 协议事实（改前的真实形状）
- 挂起的命令**在批准之前没有 commandId**：`commandId` 由 `execute()` 里的 `router.route(.submit)`
  生成，`pending_approval` 响应里只有 `approval{id,text,reasons,createdAt}`。
- 审批只有三种可观测事实：`GET /api/approvals` 列表里「在 / 不在」、`POST /api/approvals/{id}`
  的返回（只有**做决定的那台**拿得到）、300s TTL 的隐式过期。
- 所以旧客户端只能「审批消失 → 去对话转录里找提交后最新的 commandId」猜归属 —— 同对话多设备必错。

## 本轮改动
- 新增 `GET /api/approvals/{id}`（macOS `HTTPAPI.approvalStatusResponse` / Windows
  `handle_get_approval`，逐字段同构）：`pending` / `approved`(+commandId) / `denied` / `expired`
  / `failed`；未知或记录已淘汰 → 404。**知道 approvalID 就够了，不需要 conversationID**。
- `ApprovalGate`（两端）新增 `outcomes[approvalID]`：`decide` 一进来就落终态（deny→denied，
  approve→approved 且 commandId 暂空），执行成功后 `attachCommand` 补**实际** commandId，
  执行失败 `markFailed`。过期 pending 在 prune 时写成 `expired`。
- `decide` 现在**先 prune 再判定**（旧实现的 300s TTL 只在列表查询时生效，第 6 分钟仍可批准）。
- 客户端删掉 `latestCommandID` / `ConversationCommandProbe`（不再读对话转录），改轮询终态端点；
  404 时回落到「审批是否还在列表里」兼容旧桌面端（仍在 → 继续等，真消失 → 明确「结果不可用」）。
- 点批准时若审批已被别处处理（POST 404），用终态端点认领 commandId 继续轮询，
  不再把 404 显示成"命令失败"。
- Demo 后端补齐 `GET /api/approvals` 与 `GET /api/approvals/{id}`（含 TTL），否则审核员关窗后会空转。
