## 讨论（未改代码）：能否把中继跑在本机 / 集成进桌面端

用户问：「这个服务能否直接在本地启动，把本机当服务器」「集成在桌面端开启后相当于启动服务」。结论要点（已答复，供后续决策）：

- **本机跑中继 = 已支持且已实测**（形态①）：`PORT/node dist/index.js`，绑定 0.0.0.0；iPhone → 本机中继 → 本机桥（回环 WS）→ 进程内 HTTPAPI，只需暴露**一个**入站端口。
- **集成进桌面端（形态③）目前做不到「不改代码」**：中继是 Node/TS（约 1k 行），daemon 是 Swift。两条路：①把协议移植进 Swift（协议很小：4 种消息 + 设备注册 + 心跳 + 令牌校验，可行）；②随包带 Node 运行时（体积/维护成本高）。**过渡方案**：桌面端把中继当受管子进程（带启动按钮），今天就能"开桌面端≈服务起来"。
- 关键取舍：本机当服务器时，「远程可达性」依赖 Mac 常开 + 家用网络入站（NAT/端口映射/DDNS 或反代），且可用性 = Mac 可用性（睡眠/关机即断）；安全边界只有共享令牌 + 设备令牌、明文、无限流。
- **趋势分析澄清**：中继是纯转发、不存数据 → 本身不产生趋势数据。三种读法：①远程看 Mac 上 agent 的进度/趋势（可行，历史数据来自 Mac 端 commands/conversations/日志，中继只是管道）；②中继自身运行趋势（连接数/流量/掉线率）→ 现在只有 `/devices` + 日志元数据，无时序/metrics，需另加采集；③7×24 无人值守采集 → 本机当服务器最差，应上常开服务器/容器。
- 与官方口径一致的建议：真跨网络优先反代 + wss + 限流，或直接用 Tailscale/WireGuard。

## 讨论：把中继部署到服务器（公网）实现真远程

用户问「现在就可以把服务部署到服务器上实现远程了吧」。答复口径：

- **链路已就绪**：两端默认关闭、地址与令牌都可配置，指向服务器版中继即可（Mac 改 `relay.json`，
  iOS 设置页填同地址+令牌；配对仍需先同 Wi-Fi 做一次）。
- **但我未实测公网/TLS**：本机回环与局域网已验，公网只有代码层判断 → 落地前必须实测。
- 🚨 **必须先补的 4 项**：①TLS/wss（ATS 约束，明文公网大概率被拦）；②路由改 deviceId 定向
  （现为角色广播，持令牌者可收走含设备令牌的帧）；③限流/防滥用 + 重放保护（现在没有）；
  ④隐私政策 `docs/privacy.html` 与 App 隐私问卷需随「可配置中继」更新（现写「仅局域网」）。
- 部署侧最小要求：Node 20+（或 Docker）、进程守护（systemd/docker restart）、`RELAY_TOKEN` 必设、
  反代终止 TLS、只开必要端口。
- 验收清单：`/devices` 同时看到 desktop+agent → App 日志出现 `(via relay)` → 停中继验证回落 →
  重启中继验证自愈（今天在回环上已走过一遍）。
