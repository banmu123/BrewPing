# 2026-09-13 工作日志

## macOS 桌面端：composer 输入框无法输入 + 高度与 Windows 不一致（已修）

**现象（用户报）**：① 对话输入框点进去打不了字；② 输入框高度和 Windows 桌面端不一致；③ 要求布局在窗口尺寸变化时仍正确适配。

**根因（三条独立问题）**

1. **打不了字 —— `NSScrollView()` + `NSTextView(frame: .zero)` 手搓构造。**
   第一版自己 `let scrollView = NSScrollView()` + `let textView = SubmitTextView()`（无 frame）再 `scrollView.documentView = textView`。
   `documentView` 的 frame 是 `.zero`，AppKit **不会**替它布局（`autoresizingMask = [.width]` 只管宽度），文本视图既不可见也不可点击 → 「点不进、打不了字」。
   **修法**：一律用 `NSTextView.scrollableTextView()` 构造（它会把 textContainer / minSize / maxSize / autoresizingMask / widthTracksTextView 全套装好），然后自己接管高度。
   同时把「Enter 发送」从 `keyDown` 覆写改成 `NSTextViewDelegate.textView(_:doCommandBy:)` —— 后者是 AppKit 的标准拦截点，**输入法组字期间不会被调用**，不会吞掉中文候选词的回车。

2. **高度不对 —— `.frame(minHeight:maxHeight:)` 是弹性框，不是钳制框。**
   我写了 `.frame(minHeight: 72, maxHeight: 176)`。SwiftUI 的 frame 在同时给 min/max 时是**弹性**的：父级有余量就一路顶到 maxHeight，并把内容**垂直居中** → 输入框永远 176 高、文字浮在中间（第一版截图就是这样）。
   **修法**：把高度范围钳在 `NSViewRepresentable.sizeThatFits` 里（内容 52…156），外壳只留 padding，再补 `.fixedSize(horizontal: false, vertical: true)` 禁止父级拉伸。**别在 SwiftUI 侧写 min/max frame 去控高度。**
   `max-h-44` 超出后的滚动由 NSScrollView 承担：`textView.frame.height` 用**未钳制**的自然高度（这样 document 比 clip 高，才真的滚得起来）。

3. **尺寸对齐**：Windows 是 `<textarea min-h-[72px] max-h-44 px-4 pt-3.5 pb-1.5 font-mono text-sm>`，且 Tailwind 是 `box-sizing: border-box` → **72/176 包含 14+6 的上下内边距**，内容区 = 52…156。水平 16pt 走 SwiftUI padding（NSTextView 的 `textContainerInset` 只能给上下对称值，表达不了 14/6 的不对称）。
   实测：空态 72pt，6 行文本涨到约 117pt，符合预期。

**布局自适应（第三条要求）**
- 新增 `EnvironmentValues.viewportWidth`（`LatteTheme.swift`），由 `DesktopRootView` 里**唯一一个** GeometryReader 注入（只包主区，不包侧栏）。
- `ConversationColumn` 用它算 `列宽 = min(736, 可用)` 与 `留白 = 可用 < 640 ? 12 : 16`（对齐 `max-w-[46rem] px-3 sm:px-4`）。
- **不要**在会话内部逐处用 GeometryReader：它会把 VStack 的剩余高度全吃掉，composer 会被顶到奇怪的位置。
- 原先的 `ConversationColumnSimple` 用 `.frame(maxWidth: 736) + .padding(.horizontal, 16)` → 实际占 768pt 且窄窗不收缩，已删除。
- 实测：窗口 1080 → 列 736/留白 16；窗口缩到 560（主区约 340）→ 列收缩到主区宽、留白 12、下拉与目录条按 maxWidth 截断、无溢出。

**验证手段（无辅助访问权限时怎么验「能输入」）**
- `osascript` System Events 点击在本机不可用（`-25211`）。
- 改用：临时加一个 `weak var` 全局引用记下 NSTextView，`onAppear` 里若环境变量存在则
  `window.makeFirstResponder(tv)` + `tv.insertText(多行文本, replacementRange: NSRange(location: 0, length: 0))`。
  **`insertText` 就是 NSTextView 处理可打印按键时走的同一个人入口** → 能插进去就说明输入链路通；同时多行文本能验证高度是否随内容增长。
- 窗口尺寸用 `NSApp.windows.first{...}?.setContentSize(...)` 驱动（`.defaultSize` 只在首次创建窗口生效，之后 frame 是从上次会话恢复的）。
- 收尾：`grep -rn "ComposerDebug\|BREWPING_TYPE_TEST\|BREWPING_WIN_W"` 确认零残留。
- ⚠️ **python 改 Swift 字符串字面量时别用 `re.subn` 的 replacement**：replacement 里的 `\n` 会被当成转义写进文件，把 `"...\n..."` 变成真实换行 → Swift 报 `unterminated string literal`。用 lambda 或 `str.replace`。
- ⚠️ 批量改同一文件时，锚点要用「当前文件真实内容」，别用记忆里的内容 —— 中途插入过 `.onAppear` 块，锚点就失效了（`assert count == 1` 挡住了）。
