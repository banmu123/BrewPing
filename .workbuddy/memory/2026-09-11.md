## 小插曲：Mac 上"正在验证 iOS 26.3.simruntime"弹窗关不掉

跑模拟器验证时踩到的副作用，记录因果以免以后再困惑：
- **现象**：Mac 屏幕中间出现带进度条的「正在验证 "iOS 26.3.simruntime"...」弹窗，点任何按钮都没反应。
- **成因**：`xcrun simctl` 挂载/使用 simulator runtime 触发 Gatekeeper 验证，进度 UI 由 `CoreServicesUIAgent` 显示；验证完成后 UI 没撤下 → 僵尸窗口。
- **判断依据**：`xcrun simctl runtime list -v` 显示该 runtime `Signature State: Verified` / `State: Ready`（验证其实早完成了），且 `Last Used At` 正是操作时间。
- **解法**：`pgrep -l CoreServicesUIAgent` 取 PID → `kill <PID>`（**无效，它忽略 SIGTERM，PID 不变**）→ `kill -9 <PID>` 后消失。**不要 kill `simdiskimaged`**（负责挂载镜像）。
- 结论：纯 UI 僵尸，runtime 未受影响（三个 runtime 仍全部 Ready）。
- 已把这套排查写进技能 `ios-simulator-verify` 第六节。

### 追加修复：本地化引起的启动崩溃 `EXC_BAD_ACCESS (code=1, address=0x1)`

**根因**：`ContentView.swift:230`（未配对卡片 `notPairedCard`）的
`Text("Open \(BrewPingConfig.macAppName) on \(device.host), reveal its pairing code, then enter the code for this device.")`
是 SwiftUI `LocalizedStringKey`（**2 个插值**），但 `zh-Hans.lproj` 里该 key 的译文写成了
`"在 %@（%@）上打开 %@，显示配对码后在此设备上输入。"`（**3 个 `%@`**）。
运行时 SwiftUI 按中文译文去取第 3 个实参 → 读到栈上不存在的值 → `EXC_BAD_ACCESS (code=1, address=0x1)`。
进入条件很低：**有设备但未配对**（首次添加 Mac、或重装 App 后）就会走到这个卡片。

**修法（两个规则，务必牢记）**：
1. **译文的 `%@` 个数必须与代码里的插值/实参个数完全相等**；
2. **顺序不可调换** —— SwiftUI 按出现顺序填充，不要指望 `%2$@` 重排。中文语序与英文不同时，**改中文措辞去迁就顺序**，而不是重排占位符。
   本例改为 `"打开 %@（位于 %@），显示配对码后在此设备上输入。"`（2 个 `%@`，顺序不变，语义仍通顺）。

**新增防呆脚本**：`ios/Scripts/check_localization.py`（退出码 1 = 有会崩的问题）。检查三类：
① 同一 key 在 en/zh 的 `%@` 个数不一致；② 代码插值数 < 译文占位符数；③ 某 key 只在一侧（漏翻）。
已用「故意注入 3 个 `%@` → 确认报错退出码 1 → 还原」验证脚本本身有效（避免永远输出 ✅ 的假阳性脚本）。
**每次改完 strings 都跑一次**，这类崩溃常藏在低频分支（未配对、网络错误），自己点 UI 很难覆盖到。

**实测验证**：中文 + 未配对设备 → 卡片正常渲染「打开 BrewPing Desktop（位于 192.168.1.50）…」，进程存活、无崩溃日志；
英文同场景正常；中文 + Demo 设备回归正常（`/api/status`、`/api/agents` 200，轮询在跑）。

## Mac 端启动状态指示优化：B + C

**用户原话**：「打开桌面端，点击 Show Terminal 之后才变 online，不应该打开就是 online 吗？」

**根因**：Mac 端 `isRunning = true` 不是"App 进程在跑"，而是"`/api/status` 返回 online"。链路为：
```
DesktopCore.start()
  → BrewPingAgent.run()（后台 thread）
       → OpenCodeAgent.start()  ← spawn 子进程（5-10 秒）
       → HTTPServer.start()
       → BonjourAdvertiser.start()
  → startStatusPolling() 每 2 秒轮询 /api/status → 拿到 online 才置 true
```
点 Show Terminal 与状态无关，只是巧合：等得不耐烦 → OpenCode 正好 spawn 完 → 下一次 2s 轮询拿到 online。

**B 方案**：引入 `RuntimeState` 三段式（`.idle` / `.starting` / `.online` / `.offline`），`start()` 立刻置 `.starting`，`MenuBarView` 改用三态渲染：starting 灰点 + "Starting…"，online 绿，offline 红。

**C 方案**：`startStatusPolling()` 改成 `schedulePoll(intervalMs:200, maxIterations:25)`（5 秒内每 200ms），离开 starting（online/offline）即停 fast loop；切到 online 后回到稳态 2s 轮询。

**改动文件**：
- `Sources/App/DesktopCore.swift`：`enum RuntimeState`、`@Published runtimeState`、`schedulePoll(...)`、保留 `isRunning` 兼容
- `Sources/BrewPingDesktop/MenuBarView.swift`：抽 `runtimeBadge` 三态 View

**实测**（`bash /tmp/probe_startup.sh` 每 200ms curl `/api/status`）：
```
[0.02s] HTTP 502
[0.24s] HTTP 502
...
[2.04s] HTTP 502
[2.26s] HTTP 200 → {"status":"online",...}  ← backend ready
```
即 backend 在 2.26s 就绪；新轮询（200ms）下 UI 立刻反映，旧轮询（2s）下最坏延迟 4.2s。`swift build --disable-sandbox` Build complete。

**经验**：进程"已经启动"和"服务可用"是两个状态。macOS 菜单栏 App 用 NSStatusItem 时，UI 一定要把"spawn 期间"显式画出来，不要让用户以为红 Offline = 进程死了。
- Mac 端 `swift run BrewPingDesktop` 启动成功：HTTP API 绑定 `http://192.168.0.203:8787`、Bonjour `_brewping._tcp` 正常广播

**待用户/后续手动**：由于当前 Mac 菜单栏图标在测试环境不可见（既有环境问题，见上文菜单栏图标排查），本次未在 GUI 上实际点开菜单栏截图 QR；Mac 端改动已通过编译 + 启动日志确认。建议在 Xcode 真机/真 Mac 环境再补一次端到端扫码验证。

## 授权确认闭环：Safe 档 + 危险模式拦截 + iPhone 异步确认（14:12 起）

**需求**：集成 Claude Code 等智能体后，需要用户手动确认授权的操作如何处理。经讨论确定实现**最小闭环**——默认 Safe 档、危险命令模式拦截、iPhone 弹窗异步确认。

**三档授权模式**：`safe`（默认，只拦危险）／`askAll`（每条都确认）／`auto`（全免确认，等同 `--dangerously-skip-permissions`）。**默认 safe = 谨慎起步 + 渐进放权**，审核友好。

**核心机制**：
- **Mac 端检测 + 挂起**：命令在 `HTTPAPI.messageResponse` 入口先过 `ApprovalGate.shared.check(text:)`；safe 命中危险 → 生成 `PendingApproval` 挂起（不写 PTY），返回 `pending_approval`；未命中/auto → 放行走原 `executeCommand`。
- **危险模式本地内置**（`DangerPattern.swift` 正则），**不信任 agent 自报**：rm -rf、git push --force、curl|sh、sudo、chmod 777、git reset --hard、drop table 等 12 类，每类带稳定 `code`（iOS 据此本地化）+ `detail`。
- **iPhone 异步确认**：`POST /api/message` 返回 `pending_approval` → iOS `CommandSubmitter` 置 `pendingApproval` → `ApprovalRequestView` 弹窗（命令 + 原因 + 允许一次/总是允许/拒绝）→ `POST /api/approvals/:id` 决定。
- **超时默认拒绝**：Mac 端 pending TTL 300s，过期从队列 prune（不执行）；iOS 下滑关闭 = 不表态挂起。
- **"总是允许"白名单**：只记已知 danger code，持久化到 `~/.brewping/approval.json`(0600)，含 mode。

**改动文件**：
- Mac 新增：`Sources/App/DangerPattern.swift`、`Sources/App/ApprovalGate.swift`；改 `Sources/App/HTTPAPI.swift`（拦截 + `/api/approvals`、`/api/approvals/:id`、`/api/approvals/mode` 路由 + 抽 `executeCommand` 复用）

## 追加排查：切换授权模式报 401（14:54）

**现象**：Mac 端修好后，iPhone 切模式报 401（错误提示工作了，说明 iOS 是新版）。

**Mac 端接口验证正常**（curl 复现三种 401 场景）：
- 完整鉴权 → `{"success":true,"mode":"askAll"}` ✅
- 缺 timestamp/nonce → `401 missing timestamp/nonce`
- 错 token → `401 invalid token`
- 时钟偏移 300s → `401 stale request`

→ 说明 Mac 端逻辑无误，**401 来自 iPhone 侧鉴权**。两种可能：① 设备**未配对**（Keychain 无 token，`BrewPingHTTP.request` 不加 Authorization 头 → `missing bearer token`）；② 已配对但 **token 失效**（`~/.brewping/pairing.json` 在 13:07 有过重建）。

**发现的两个 iOS 端缺陷并修复**：
1. **未配对时也显示模式行** → 必然 401，用户只会觉得"坏了"。`approvalModeRow` 的显示条件从 `hasDevice` 收紧为 `let device = activeDevice, DeviceAuth.isPaired(device)`；`ApprovalModeStore.refresh` 同步加 `DeviceAuth.isPaired` 守卫。
2. **401 只显示状态码，看不到服务端原因** → `setMode` 改为读响应体：401 单独提示"Not paired with this Mac. Enter the pairing code in this device's settings."；其他错误显示服务端 `error` 字段（`Couldn't switch approval mode: %@`）。本地化 key 同步替换（en/zh），`check_localization.py` 通过。

**教训**：客户端的"设备存在" ≠ "可通信"。任何依赖鉴权的 UI，都要用 `DeviceAuth.isPaired` 判定，而不是 `hasDevice`。

## 追加排查：AI Agents 区一直显示"检测中"（14:56）

**现象**：iPhone 上 "AI Agents" 区永远停在 `Detecting agents...`。

**根因（与上面的 401 同源，是它的第三个表现）**：
- `ContentView.refreshAgents()` 原来写的是 `let (data, _) = try await ...`，**完全忽略 HTTP 状态码**；401 时 decode 失败 → `agents = []`，且不区分原因。
- `agentListCard` 的空态文案只看 `online`：`online ? "Detecting agents..." : "No agents detected..."`。
- 而 **`/api/status` 是公开端点**（`HTTPAPI.handle` 里在 `authorize` 之前就返回），token 失效时它**仍返回 200** → `refreshStatus()` 里那个 401 分支（`statusError = "Not paired with..."`）**永远不会命中** → `online = true`。
- 于是 `agents.isEmpty == true && online == true` → 界面永远"检测中"。

**修复**：加 `@State agentsUnauthorized`，`refreshAgents()` 检测 `BrewPingHTTP.isUnauthorized(response)` 时置 true；`agentListCard` 空态改为三分支：**鉴权失败 → "未配对…"** / Mac 离线 → "No agents detected" / 其他 → "Detecting agents..."。

**教训（重要，与上一条呼应）**：`/api/status` 公开是有意的（DesktopCore 本机判活要用），但**不能拿它当"鉴权正常"的证据**。凡是需要 token 的界面状态，都要以该端点自身的 401 为准，而不是看 `online`。

## 修复：Watch 端模型切换"滑动无效"

**现象**：用户报 Watch 上模型滑动选择时滑不动。

**根因**（代码证据）：
- `ios/Watch/WatchSessionManager.swift` 的 `stepModel(by:)`（L86-91）用取模做环形切换，数据层**没有问题**。
- `ios/Watch/ContentView.swift` 的 `modelSwipeSection`（L174-220）在改用"箭头按钮"后，**整个区域没有绑定任何滑动手势** —— 只有两个 `chevron.left/right` 按钮。
- 而最外层是 `ScrollView`（L23），横向拖拽落在该行上时无人识别，事件冒泡给 ScrollView；ScrollView 只处理纵向，横向被忽略 → "划不动"。
- 更误导的是提示文案当时写的是 `← switch model →`，**暗示可以滑动**，实际只有按钮能点。
- 背景：这里当初刻意从 `TabView(.page)` 换成按钮（避开"矮 TabView 渲染空白"的坑），但**换交互时漏了滑动**。

**修复**：给该行加 `.contentShape(RoundedRectangle(cornerRadius: 6))` + `.simultaneousGesture(DragGesture(minimumDistance: 20).onEnded { ... })`，判定 `abs(dx) > 30 && abs(dx) > abs(dy)` 才 `stepModel(by: dx < 0 ? 1 : -1)`。用 `simultaneousGesture` 保证不抢按钮点击；文案改为 `← swipe model →`（en/zh 同步）。watchOS `BUILD SUCCEEDED`、`check_localization.py` 通过。

**触发场景**：横向滑（左/右）无响应；纵向滑被 ScrollView 正常消费；斜向滑无明确归属；`models.count <= 1` 时整区隐藏（`canSwitchModel=false`）无元素可滑；只有精确点 chevron 才能切换。

**遗留提示**：设备区（`deviceSwipeSection`）与 Agent 区（`agentSwipeSection`）仍用 `TabView(.page)` 且嵌在 `ScrollView` 里（`frame(height: 40/52)`），存在同样的"纵向滚动 vs 横向翻页抢手势"隐患，本次未改。

## 修复：Watch 切 Agent 后模型列表不跟着换（15:33）

**用户提问**："模型应该是一一对应 agent 配置的吧" —— 确认设计意图时暴露出一条断链。

**设计确认**：模型**确实是 per-Agent** 的（Mac 端 `GET /api/agents/<agentId>/models`，底层 `AgentConfigDiscovery` 读各 Agent 自己的配置文件），用户的期待正确。

**断链根因**（在 iPhone 侧）：
- `WatchConnectivityManager.switchMacAgent(to:)`（L293-322）在 `POST /api/agents/<id>/switch` 成功后**只打了个日志就结束了** —— 既不刷新该 Agent 的模型，也不向手表推送。
- 结果：手表切 Agent 后仍拿着**上一个 Agent 的模型列表**；只能指望 iPhone 下一轮 2s 轮询"顺带"纠正（时序窗口最大 2s + 一次网络往返）。
- 更糟的是 Watch 端 `applyModels` 里 `guard !parsed.isEmpty else { return }`（空列表保留旧值）—— 当新 Agent 模型尚未拉到/为空时，会**保留旧 Agent 的模型**，错位就此持久化。

**修复（三处）**：
1. `WatchConnectivityManager`：`switchMacAgent` 成功后 `await refreshModelsAndPush(for:device:)`；新增该方法（拉 `ModelStore` 再 `pushStatus`）。**标 `@MainActor`** —— `ModelStore` 是 `@MainActor` 隔离的，否则报 `expression is 'async' but is not marked with 'await'`。
2. `WatchConnectivityManager`：新增 `knownModelsAgent` 属性；`pushStatus` 与 `requestStatus` reply **两处** context 都加 `"modelsAgent"`。`ContentView.refreshModels()` 同步写入 `watchBridge.knownModelsAgent = activeAgentID`。
3. `WatchSessionManager.applyModels`：加归属校验 —— `modelsAgent != activeAgentID` 时**清空** models（`activeAgentID` 在 `switchToAgent` 里是立即更新的，所以切 Agent 瞬间即命中）。

**验证**：iOS `BUILD SUCCEEDED`、Watch `BUILD SUCCEEDED`。真机需实测"切 Agent → 模型列表立刻换成该 Agent 的"。

## 修复：切 Agent 被弹回 OpenCode（15:39）

**现象**：用户反馈切到 Claude Code 后**自动跳回 OpenCode**，切不过去。

**根因**：这是**上一条修复引出的回归**。
- `currentAgentID` / `currentAgentName` / `currentAgentMode` **只在 2s 轮询的 `refreshStatus()` 里更新**（`ContentView.swift` L1239 等），刚切完时仍是旧值。
- 我新增的"切 Agent 成功后立刻 `pushStatus`"用的是**旧** `currentAgentID` → 推给手表的 `activeAgent` 还是 `opencode`。
- 而 Watch 的 `applyContext`（`WatchSessionManager.swift` L149-152）**无条件**用 context 的 `activeAgent` 覆盖 `activeAgentIndex` → 手表刚切到 Claude Code 就被弹回 OpenCode。

**修复（两端）**：
1. **iPhone**：`refreshModelsAndPush` 里**先**把 `currentAgentID` / `currentAgentName`（从 `knownAgents` 查名）/ `currentAgentMode` 赋成新 Agent，**再**拉模型、推送。
2. **Watch**：`applyContext` 加 `pendingAgentSwitch` 保护 —— `switchToAgent` 时记下本地目标 Agent，收到与目标不一致的 `activeAgent` 时若还在 5 秒保护期内就**忽略**（保持本地选择）；一旦服务端回推的值等于目标即确认并解除保护；超过 5 秒未确认则放弃保护（视为切换失败，接受服务端状态）。

**验证**：iOS + Watch 均 `BUILD SUCCEEDED`。

**教训**：给"本地乐观更新 + 服务端权威值"的链路补"立即推送"时，必须同时检查**被推送的那个值是不是也刚更新过** —— 否则乐观更新会被滞后缓存反向覆盖。

## 修复：手表切 Agent，iPhone 的"Default"标记不变（15:42）

**现象**：在手表上切 Agent，iPhone App 里显示的默认 Agent 不跟着变。

**根因**：`ContentView.runStatusLoop` 的结构是
```swift
await refreshStatus()
await refreshAgents()        // ← 只在进入循环前执行这一次
while !Task.isCancelled {
    try? await Task.sleep(5s)
    await refreshStatus()    // ← 循环里只有这个
}
```
**`refreshAgents()` 在轮询循环里从不被调用**。所以外部（手表 / Mac 菜单栏）切 Agent 后，iPhone 的 `agents` 数组不重新拉取，`agentListCard` 里的 `"Default"` 标记（来自 `GET /api/agents` 的 `active` 字段）永远停在旧值。

**修复**：
1. `refreshStatus()` 里加变化检测：`let newAgentID = decoded.session?.agent`，与 `sessionAgentIDFromStatus` 不同则 `await refreshAgents()`。覆盖**所有** Agent 变更来源（手表、Mac 菜单栏、iPhone 自己）。
2. 手表切 Agent 成功后 `post(.watchDidSwitchAgent)`；`ContentView` 用 `.onReceive` 立即 `refreshStatus() + refreshAgents()`，让界面**即时**反映（不必等 5s 轮询）。App 后台时监听不触发，由第 1 条兜底。

**验证**：iOS `BUILD SUCCEEDED`。

**顺带澄清**：状态轮询间隔是 **5 秒**（不是之前以为的 2 秒）。
