## 截断与 Markdown 完整性审查（傍晚）

用户问：「是否等回复完才做 Markdown？万一截断如何保证完整性？」

### 结论 1：是真的「落库后才 Markdown」，且渲染层对截断**容错良好**
- `ChatView`：`isStreaming && id.hasPrefix("streaming_")` → `StreamingAssistantMessage`（纯文本+光标）；
  落库后 run 被清 → 转录消息走 `MarkdownView`（完整解析）。**Markdown 只渲染一次**。
- `MarkdownBlock.parse` 的围栏处理：`while index < lines.count, !hasPrefix("```")` ——
  未闭合围栏会把剩余全部行吃进 body 并渲染成「到底的代码块」，**不崩、不丢内容**。
- 内联语法（`**粗`、`` `code ``、`[文](链`）未闭合时 `range(of:)` 返回 nil → 落回逐字符
  buffer → **原样显示字面量**，不会吞掉后续文本。
⇒ 渲染层最坏只是少几个符号的样式，不会「显示不全」。

### 结论 2：但**内容层**有两个真实缺口（本轮已修）
🚨 **这是「不完整」的真正来源，不是 Markdown。**
- **缺口 A：失败 / 被停止时半截回复被丢弃。**
  `CommandRunner.finish` 的 `.failed` 分支原先**只落 error 条目**，且失败时 `response/rawOutput`
  均为 nil → 连终态 delta 都不发。用户看着生成到一半点「停止」，半截内容**从界面凭空消失**。
  ✅ 修：`runHeadless` 失败分支改用 **`lastStreamText`**（流式期间最后一帧累积全文，即用户
  实际看到的内容）作为 `response` 传入；`finish` 的 failed 分支**先落 assistant 再落 error**，
  阅读顺序 = 半截回复 → 为什么停在这里。取 `lastStreamText` 时补了 `streamLock`（它由
  readabilityHandler 后台线程写）。
- **缺口 B：headless 超时归因误导。**
  `SystemCommand.run` 超时也返回 nil（与启动失败同路），`HeadlessCLIAgent` 一律报
  「Failed to launch …」→ 把「跑很久被掐掉」说成「根本没起来」。
  ✅ 修：文案改为「did not finish within Ns and was stopped」，并在注释里说明
  能走到该分支说明 `detect()` 已确认可执行文件存在。
  （未改 `SystemCommand.run` 返回契约 —— 它还有 3 个调用点（探测版本 / 环境安装），
   改契约风险大于收益；部分内容改由 `lastStreamText` 兜底，效果相同。）

## 修复「执行中切换对话 → 切回来显示异常」

### 根因（三处同源）
1. **主因**：`run` 是**单值字段**，而 `updateActiveConvId` → `cancelRunTracking()` → `clearRun()`
   在切对话时把它清空。切回来时 `run == nil`，但 `isBusy` **回退到**
   `activeConv?.latestCommandId != nil` = true → 界面出现「有停止按钮、却没有任何状态说明」，
   已生成的半截回复也一并消失。
2. **同类兜底缺口**：若 `runs` 里根本没有该对话的条目（App 重启后恢复、
   或命令由手机端 / Watch 端发起且桌面端尚未收到任何增量），同样 isBusy 真、指示器空。
3. **附带**：`acceptDelta` 只接受 `delta.conversationId == activeConvId` 的帧 →
   切走期间原对话的增量被丢弃 → 切回时文本停在切走那一刻。

### 修复（`Sources/BrewPingDesktop/DesktopAppState.swift`）
- 🚨 **核心：`run` 单值 → `runs: [String: ConversationRun]` 按对话保存**
  （key = conversationId；草稿态用 `draftRunKey = "__draft__"`），
  `public var run: ConversationRun? { runs[currentRunKey] }` 供 UI 读取。
- `cancelRunTracking()` 不再清 `runs` —— 只作废 `busyTimer` 与就地 `runError`。
  这是「切换即丢状态」的直接凶手。
- `acceptDelta` **按 `delta.conversationId` 分桶**：已跟踪的对话（含刚切走的）继续更新；
  从未跟踪且非当前对话的帧忽略（不为历史对话凭空造状态）；
  当前对话的陌生帧（手机端发起）建立跟踪。
- `pendingDelta` → `pendingDeltas: [String: ConversationDelta]`，`flushDelta` 遍历分桶。
- `syncRunTick` 遍历**所有**对话评估 stalled（切走的对话也要判）。→ logs/UI 一致。
- `clearRun()` 改为只清**当前对话**的条目。
- `reconcileRun`：① 按 conv.id 取；② **无条目但 `latestCommandId` 非空 → 补一条 thinking**
  （覆盖 App 重启 / 手机端发起的兜底，保证 isBusy 与指示器一致）；③ 终态只清该对话。
- `send` 新增 `migrateRun(to:)`：乐观占位先挂草稿键，拿到真实 convId 后**迁移**过去
  （否则切走再切回找不到这条命令的状态）。
- `archiveConversation` / `deleteConversation` 清 `runs[id]`，防字典随时间堆积。
- `updateActiveConvId` 去掉 `resetRun` 参数（切换一律保留状态，不再需要区分）。

验证：编译 ✅、`swift test` **59/59** ✅、`build-app.sh` ✅、重启 ✅（进程 51892 / 8787）。
